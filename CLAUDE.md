# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

OwlPilot is a class-schedule app built for a hackathon. It has two independent npm projects with no shared root `package.json`:

- `app/`: React Native + Expo (TypeScript), run in **Expo Go** (no native builds, so only Expo Go-compatible packages).
- `server/`: small Express (CommonJS) API. It is the only thing that talks to Gemini, so the API key never ships in the app.

The UI is designed in Figma (file key `22ozX0doqUgl5Svih1DqjR`, page "Page 1"). Use the Figma MCP to read frames before building a screen. Real KSU data (sections, professors, reviews) lives in `app/src/data/` (see its README). Built so far: Splash, Welcome, About You (Step 1, Academic Profile), Select Courses (Step 2), Schedule Preferences (Step 3), and Building (animated owl) and Results (Figma frame `73:815`), Home (with bottom tabs), and placeholder Calendar, Profile and FindClass screens.

## Commands

```bash
# server (port 3000, or PORT from server/.env)
cd server && npm install && npm start

# app
cd app && npm install
npx expo start          # scan the QR code with Expo Go; add -c to clear the cache after editing app/.env
npx tsc --noEmit        # typecheck
npm run test:scheduler  # runs the scheduler for a demo student and prints the schedules (add `-- extra` for a 6-course case)
npx expo install <pkg>  # always use this instead of npm install, so versions match the Expo SDK
```

There are no automated tests (only the scheduler script above). Smoke-test the server with `curl localhost:3000/health`.

## Architecture

**Request flow:** app screen → `app/src/api.ts` (`askGemini`) → `POST {EXPO_PUBLIC_API_URL}/api/ask` → `server/index.js` → Gemini REST API (`generateContent`, key sent in the `x-goog-api-key` header). The app must never call Gemini or any third-party API directly; add new endpoints to `server/index.js` and a wrapper function in `app/src/api.ts`.

**Environment files** (all git-ignored except `.env.example`, and `.claude/settings.json` denies reading any `.env`):
- `server/.env`: `GEMINI_API_KEY`, optional `PORT`, optional `GEMINI_MODEL` (default `gemini-3.5-flash-lite`; `gemini-2.5-flash` and `2.5-flash-lite` now return 404 for new API keys, and the bigger 3.x flash models often return 503 "high demand"). The user pastes the key themselves; never ask for it.
- `app/.env`: `EXPO_PUBLIC_API_URL`. It must be the computer's Wi-Fi IP (e.g. `http://10.0.0.45:3000`), not `localhost`, because Expo Go runs on a phone. Only `EXPO_PUBLIC_*` variables reach the app bundle, so never put secrets there.

**Navigation:** React Navigation native stack, defined in `app/App.tsx`. Route names and their params live in `RootStackParamList` in `app/src/navigation.ts`. To add a screen, add it to that type, register a `Stack.Screen` in `App.tsx`, and type its props with `NativeStackScreenProps<RootStackParamList, "Name">`. `Splash` uses `navigation.replace("Welcome")` after 2 seconds so Back doesn't return to it. Flow so far: Splash → Welcome → AboutYou → SelectCourses → Preferences → Building → Results.

**Fonts and theme:** `App.tsx` loads the fonts with `useFonts` and holds the native splash (`expo-splash-screen`) until they're ready. The font keys in `app/src/theme.ts` (`fonts.title`, `fonts.body`, ...) must match the names loaded in `App.tsx`; when you need a new weight, import it in both places. Use **Outfit** for headers and titles and **Manrope** for everything else, as in the Figma design. Poppins appears in Figma only on one old title layer and a notes frame, so don't use it. Colors come from `theme.ts` (yellow `#FFC629`, black, white, light gray `#F5F5F5`), so don't hardcode hex values in screens.

**Shared profile data:** `app/src/context/ProfileContext.tsx` is a plain React Context (`ProfileProvider` wraps the navigator in `App.tsx`; read it with `useProfile()` → `{ profile, setProfile }`). `Profile` holds `major`, `year` (Freshman/Sophomore/Junior/Senior), `startYear`, `gradYear` (numbers) and `takenCourses` (course *codes* like `"CS 1301"`). `aiRules` (`AiRules`, set by Building) holds what Gemini understood from the notes. `acceptedSchedule` (a `Schedule`, set by Results on "Accept Schedule") is the chosen schedule. `semester` ("Spring 2027"), `campus` ("Kennesaw"/"Marietta") and `selectedCourses` (codes) are saved by SelectCourses. Fields are `null`/`[]` until the screen that owns them saves on Continue; each screen saves with `setProfile({ ...profile, ... })` so it keeps the other steps' data.

**About You screen (`AboutYouScreen.tsx`):** major is prefilled from the Welcome route param and validated against `majors` like Welcome. Year uses `Chip`s; start year (2020–2027) and graduation use `Dropdown`. Graduation options are start year to start year + 8 and the dropdown is disabled until a start year is chosen. If a new start year is after the chosen graduation year, graduation is cleared and a red "Graduation year can’t be before your start year." shows. Previously taken courses (optional) come from `src/data/courses.ts` (`courses`, `courseLabel`, `findCourse`; each `Course` has `code`, `title`, `level` 1000–4000, `prerequisites` codes and `isElective`). The list is built from the unique courses in `sections.json` (labs like CSE 1321L are left out because the scheduler pairs them automatically); prerequisites are a hand-written, approximate map in that file (the section data has none); picking one adds a `RemovableChip`, and added courses are hidden from the search list. Continue requires major, year, start year and graduation year; otherwise red errors show and it doesn't navigate.

**Select Courses screen (`SelectCoursesScreen.tsx`):** semester dropdown (next 4 terms, default Spring 2027) and campus dropdown (Kennesaw/Marietta, default Marietta) use `Dropdown` with its `label` prop. "Find your courses" is a `clearOnPick` `SearchSelect` that hides taken and already-selected courses. Selected courses are `SelectedCourseCard`s (max 8, no duplicates). "Options for You" shows up to 5 `RecommendationRow`s from `recommend(profile, selectedCodes)` in `src/logic/recommend.ts`: courses in the degree plan (`src/mock/degreePlans.ts`, `getDegreePlan(major)`: the Computer Science list uses real KSU codes (CSE 1321, CSE 1322, CSE 2300, CS 3305, CS 3410, CS 3502, CS 3503, CS 4306, CS 4308, CS 4850, MATH 1190, MATH 2202, ENGL 1101/1102, HIST 2111, POLS 1101); other majors get a small general core list. Electives are PSYC 1101 and the AI courses, marked `isElective` in `data/courses.ts`) that aren't taken or selected and whose prerequisites are all in `takenCourses`, sorted with levels that fit the year first (Freshman 1000, Sophomore 1000–2000, Junior 2000–3000, Senior 3000–4000), then by level. Continue needs at least 1 selected course (red error otherwise), saves semester/campus/selectedCourses and goes to Preferences.

**Preferences screen (`PreferencesScreen.tsx`):** `Profile.preferences` is `{ numCourses, days, times, numOnline, notes, busyTimes }` (`Preferences` type in `ProfileContext.tsx`). Number of courses is a `Dropdown` of 1 to min(6, selected courses); default is 5 or the selected count if smaller. Preferred days (Mon–Fri `Chip`s) and class times (Morning/Afternoon/Evening/Anytime) are multi-select and each needs at least 1; "Anytime" clears the others and picking any other clears "Anytime". Online classes is a `Dropdown` of 0 to numCourses and is lowered if numCourses drops below it. Notes max 300 characters with a counter. "When can’t you take classes?" is optional: `BusyTimeModal` (days, start, end in 30-min steps, 7 AM–10 PM, end must be after start) adds `RemovableChip`s, max 5, saved as `busyTimes: [{ days, start, end }]` where start/end are **minutes after midnight** (2:00 PM = 840). Days/times constants and `formatTime`/`busyTimeLabel` live in `src/data/schedule.ts`. Layout follows Figma frame `22:391`: class times are `TimeCard`s (150×83, small range text, check icon when selected), days are evenly stretched `Chip`s, the two dropdowns use `Dropdown compact` (40px, labels like "5 classes"), and the buttons use `PrimaryButton` with `fontSize` (slim) and the `outline` variant for Skip. "Generate My Schedule" validates, saves, and goes to the placeholder `Building` screen. "Skip Without Filters" saves defaults (default course count, all days, Anytime, numOnline = numCourses i.e. any, empty notes, no busy times) and goes to the same screen.

**Component notes:** `Dropdown` (modal list, `error`/`disabled` props, optional `label` for the taller Figma style with a small label above the value), `SelectedCourseCard` (yellow card with "x"), `RecommendationRow` (course + reason + yellow "+"), `RemovableChip` (gray pill with "x"). `SearchSelect` has `emptyText` and a `clearOnPick` mode (picking calls `onSelect` and empties the box; typing never picks) for multi-add lists. `Chip` takes a `style` prop and `PrimaryButton` an `arrow` prop (plus `fontSize` and an `outline` variant).

**AI preference parsing:** `POST /api/parse-preferences` in `server/index.js` takes `{ notes, days, times, busyTimes, numCourses, numOnline }` and returns `{ hardRules, softRules, summary }`. `hardRules` are times the student can't have class (`{ day: "Mon".."Fri", start: "HH:MM", end: "HH:MM" }`, within 07:00–22:00; "only free 9–10 AM" becomes the blocked time around it). `softRules` are `{ type, value, note }` with `type` one of avoidLongGaps, maxClassesPerDay, preferDay, avoidDay, preferTime, avoidTime, interest (one rule per liked subject, for picking electives later), other. `summary` is 2–5 friendly bullets. Empty notes return empty arrays without calling Gemini. Gemini is called with `responseMimeType` + `responseSchema` (don't send `thinkingConfig.thinkingBudget`, Gemini 3.x rejects it), and the reply is validated (bad days/times/types dropped). Reliability: each call times out after 12s; 503, 429, timeouts and bad JSON are retried up to 2 more times (waits of 1s then 2s), a non-retryable error like 404 skips straight to the fallback model, and when the main model fails the same loop runs on `GEMINI_FALLBACK_MODEL` (default `gemini-3.1-flash-lite`). The whole request is capped at about 25s. Successful results are cached in memory by the exact input (max 200 entries, cleared on restart), so a repeated request returns instantly; errors are never cached. On any failure the server still answers 200 with empty arrays plus `error: "AI unavailable"`, so the app never crashes. The prompt says the notes override the chips and forbids inventing rules. Hard rules are only for times the student truly can't attend ("I work", "I can't", "I'm not available", practice); dislikes ("hate", "prefer not", "would rather not") become soft rules (`avoidDay`/`avoidTime`) and add no hard rule. Only the error message is logged, never the key. The app wrapper is `parsePreferences()` in `src/api.ts` (never throws, 30s abort so the app outlasts the server's 25s limit).

A seat isn’t guaranteed." The professor's short AI summary shows above that. **Find My Class (camera):** `FindClassScreen.tsx` gets `{ building, room, course }` (target = `Q-207`). Top yellow card "Going to Q-207 · CS 4306", a full camera preview (`expo-camera`) with a frame and a big "Scan" button. One photo is taken only when Scan is tapped, resized to 768px wide and saved as JPEG 0.5 with `expo-image-manipulator`, then `readSign()` in `api.ts` (never throws, 30s abort) sends the base64 to `POST /api/read-sign`. While waiting the button says "Reading sign…". Results: a room on the map → "You’re near Q-115 (floor 1)" + numbered steps; the main entrance (`entrance`, floor 2) and stairs/elevators (`<type><floor>_s`, the lobby ones; stairs and elevators exist on every floor, so the floor is the last known one, default 1, with a "Not floor 1? Switch to floor 2" link) are used as the location; restroom/exit aren’t placed; the scanned room is the target → green "You’re here!" card with the course and "Starts in X min" (`logic/classTiming.ts`, uses `demoClock`); nothing readable or confidence under 0.4 → "Couldn’t read a sign. Move closer and try again."; a room not on the map → "Q-xxx isn’t on our map yet." "Pick my location" opens a list of map rooms and landmarks and is also the fallback when camera permission is denied (the screen asks nicely first). `data/buildingQ.json` is the **real** map of Building Q from the floor 1 and 2 evacuation plans (92 nodes: rooms `Q-1xx`/`Q-2xx`, hallway nodes, stairs/elevators such as `stairs1_s`/`stairs2_s` (same suffix on both floors), restrooms, a vending landmark; x = meters east, y = meters south). Each room connects to door hallway nodes; the main entrance is node `entrance` on **floor 2**. `logic/indoorRoute.ts` runs Dijkstra (`routeSteps(fromId, toRoomId)`: stairs cost 8 m per floor, elevator 12 m) and turns the path into steps ("Walk about 20 m", "Turn left", "Take the stairs up to floor 2", "Q-207 is on your right"; left/right from the coordinates). `POST /api/read-sign` takes `{ image: base64 JPEG }` and returns `{ kind: "room"|"landmark"|"none", room: "Q-207"|null, allRooms: [...], landmark, confidence }` (real signs show only the number and often two side by side, e.g. "206 CLASSROOM" and "207 CLASSROOM": `allRooms` lists every visible room and `room` is the one closest to the photo center) (the server normalizes to "<letter>-<number>": "Q 207"/"Q207" become "Q-207", a visible building letter is kept ("J 1111" becomes "J-1111"), and only a bare number like "207" is assumed to be building Q); it reuses `parseWithGemini` (the image is an optional last argument: retries, fallback model, 25s cap), is not cached, never logs the image, and on failure answers 200 with `{ kind: "none", error: "AI unavailable" }`. The response schema uses plain strings (an empty string means none); enums and nullable fields made the model answer "none" for clear signs. `express.json` limit is 5 MB for the photo.

**AI schedule explanation:** `POST /api/explain-schedule` in `server/index.js` takes `{ preferences (strings: aiRules.summary + chips), strategy, badges, classes, alternatives, reviews }` for ONE schedule. `classes`/`alternatives` have `course, title, professor, rating, difficulty, wouldTakeAgain, meets, tags` (alternatives also `replaces`, `reason`); `reviews` maps professor name → up to 5 reviews (`course, quality, difficulty, text`). It returns `{ why, professors: [{ name, summary }] }`: `why` is 2–3 sentences with concrete trade-offs; `professors` has one 1–2 sentence balanced summary for every professor in the classes AND the alternatives, based only on the given reviews (a professor with no reviews always gets exactly "Not enough reviews yet", enforced by the server, not the model). The server reuses the same Gemini loop as parse-preferences (`parseWithGemini(prompt, schema, clean, label)`: retries, fallback model, 25s cap), caches results in memory by the cleaned input, and on failure answers 200 with `{ why: "", professors: [], error: "AI unavailable" }`. The app wrapper is `explainSchedule()` in `src/api.ts` (never throws, 30s abort); `logic/explain.ts` builds the request (`buildExplainRequest`) and the cache key (`explainKey` = courses + professors + times + AI summary). `ResultsScreen` requests an explanation only for the open tab the first time it is shown, keeps it per key in state, and a swap changes the key so a new one is requested. Reviews come from `reviewsFor(professor, 5)` in `src/data/reviews.ts` (only 11 professors have reviews so far).

**Real data (`app/src/data/`):** `sections.json` (801 Spring 2027 sections, 57 courses) is about 300 KB, so **never open it in full** (`.claude/settings.json` denies reading it; look at `sections.sample.json` and `README.md` for the format, or summarize it with a small node script). The app imports it normally through `src/data/sections.ts`, which exports typed `sections`, `professors` and `findProfessor(name)` (ratings from `professors.json`; unknown professor = "No ratings yet"). `reviews.json` (small, 51 reviews) is read through `src/data/reviews.ts` (`reviewsFor`); only the reviews of professors in the shown schedule and its alternatives are sent to the server.

**Scheduler (`src/logic/scheduler.ts`, plain code, no AI):** `buildSchedules({ major, year, takenCourses, campus, selectedCourses, preferences, aiRules })` returns `{ schedules (one per strategy, up to 3), notes }`. Each `ScheduleItem` has the lecture `Section`, its `lab` (paired automatically when `<code>L` exists and does not overlap the lecture), `professor`, `rating`, `blocks`, `online`, `waitlist`, `waitCount`, `suggested`, `suggestedReason`; `meetingLines(item)` gives display text like "Mon, Wed 11:30 AM–12:25 PM · Q 311".
- *Sections used:* the chosen campus ("Marietta" → "Marietta Campus") plus online (`KSU Online`, `eCore`, or mode "Fully at a Distance"/"Predominately at a Distance"; hybrids count as in person, not online).
- *Hard rules:* no overlaps (10 min travel only between two in-person classes), `busyTimes`, `aiRules.hardRules`, online count ≤ `numOnline`.
- *Full sections:* never a normal pick. A full section is tried only for a course where no open section fits with the classes already chosen, and only if its waitlist has room (`waitCount < waitCapacity`); it gets `waitlist: true` plus `waitCount` and a -15 score. Suggested courses are never waitlisted.
- *Score (higher is better):* +8 per course, (rating − 3) × 4 (no ratings = 2.5, below average, and the item gets the `noRatings` tag), (3 − difficulty) × 1.5, −3 per class-day outside the preferred days, −2 per class-day outside the preferred times, −2 per day on campus, soft rules (preferDay/avoidDay ±3, preferTime/avoidTime ±2, avoidLongGaps −3 per gap over 2 h, maxClassesPerDay −5 per extra class, interest +3), −15 for a waitlist pick.
- *Filling slots:* if `numCourses` > selected courses, open slots are filled (max 6 candidates, tagged `suggested`) in this order: (1) electives matching an `interest` rule that fit the year (juniors may also take 2000-level ones, e.g. AI 2000, if prerequisites are met; they score +10 vs +6 for core courses and are not penalized for level), (2) degree-plan courses that fit the year, (3) other not-yet-taken degree-plan courses (required core, any level). Fitting levels: Freshman 1000, Sophomore 2000, Junior 3000–4000, Senior 4000; a suggested course outside them gets −4. A course in `takenCourses` (codes are normalized) is never scheduled or suggested (a taken course in `selectedCourses` is dropped with a note), and a course whose prerequisites are not all in `takenCourses` is never suggested. (We could not reproduce the ENGL 1102 case; `recommend()` already filtered taken courses, so the guard is now applied again in the scheduler.) If `numCourses` < selected, it picks the best subset. If a selected course cannot fit, it is dropped and a note says so.
- *Speed:* max 5 best options per course (plus 3 best-professor ones; 12 on a second try if nothing fits), duplicate sections (same professor/times/room) collapsed, search stops at 30,000 complete schedules. The top 3 differ from each other in at least 2 courses when possible.
- *Fillers fit the chips:* a suggested (filler) course may only use sections where every class is on a preferred day and in a preferred time (`fitsPreferences`; async online fits), so it never adds a day like Friday for a Mon–Thu student. If a candidate has no fitting section the next candidate is tried; if the schedule still has fewer courses than `numCourses` because of that, the slot stays empty and `notes` gets "Couldn’t find a 5th course that fits your days and times." (red on Results).
- *Online slots:* selected courses get first claim. A suggested (filler) course may be online only if no selected in-person course could take an online section (that fits the rest of the schedule) with a professor rated at least 0.5 higher (`ONLINE_PRIORITY_GAIN`); schedules that break this are dropped in the search, so a different filler is picked instead. `Schedule.onlineNote` says who uses the slots ("Your 1 online slot is used by CSE 2300 (Zhang, 4.7★)", filler marked ", suggested") and shows under the tab highlight.
- *Strategies:* each `Schedule` has `strategy` (`"best" | "professors" | "fewestDays" | null`) and `highlight`. `buildSchedules` picks one schedule per strategy from the same search, among schedules with the most courses (so none wins by dropping a course): *best* = highest balanced score (preferred days/times, professors, soft rules); *professors* = highest average rating (balanced score breaks ties); *fewestDays* = fewest days on campus (balanced score breaks ties). All still obey the hard rules. A strategy whose best schedule is identical to one already chosen gets no tab: the earlier tab gets a badge instead (`Schedule.badges`: "⭐ Also the highest-rated option" for professors, "📅 Also the fewest days" for fewestDays; shown as yellow pills under the highlight and cleared by a swap), so the screen can show 1–3 strategy tabs. `highlight` is built from the data by `highlightFor`: best = "all classes fit your preferred days and times, avg 3.4★" or "N classes outside your preferred days or times, avg …"; professors = "N classes rated above 4★, avg …"; fewestDays = "only N days on campus".
- *Item tags and per-course alternatives:* each `ScheduleItem` has `tags` (`noRatings`, `outsidePreferredTime` = a class outside the chosen time chips), `level`, and `alternative: { item, reason } | null`: one better section of the same course (professor rated ≥ 0.8 higher, max 1 per course) that was skipped because it is full (`"full, waitlist N/M"`, only if the waitlist has room), outside the preferred times (`"outside your preferred time"`) or online when `numOnline` is 0 (`"online"`). It never breaks busy times, AI hard rules or conflicts with the rest of the schedule.
- *More options:* `getNextSchedule(input, alreadyShown)` returns the best balanced schedule that differs from every already shown schedule in at least 2 courses or professors (or `null`), for the "+ Find another" tab. It reruns the search, so pass every schedule shown so far.
- *Test:* `npm run test:scheduler` (`app/scripts/test-scheduler.ts`, compiled with `scripts/tsconfig.json` into `node_modules/.cache`) runs a junior CS student at Marietta (taken CSE 1321/1322, MATH 1190, ENGL 1101/1102; CS 3305, CSE 2300, AI 4732, CS 3503; 5 courses, Mon–Thu, Morning + Afternoon, 1 online, busy Fri 1–6 PM, interest AI) with interest only, without AI rules, with "I work Tuesday evenings" (hard-coded rule, Gemini is not called), then two `getNextSchedule` calls. For each case it prints the 3 strategy schedules with their highlight line, then tags and alternatives.

## Conventions

Keep code simple and student-level: plain `StyleSheet`, `useState`/`useEffect`, no state or UI libraries. Screens go in `app/src/screens/`.

All new screens must use `src/theme.ts` (colors, fonts, shadow) and the reusable components in `src/components/` (`PrimaryButton`, `SearchInput`, `SearchSelect`, `Chip`, `StepHeader`, `SectionTitle`) instead of hardcoding styles. Add any missing color to `theme.ts`. Wrap every form screen in `ScreenContainer` so the keyboard never covers inputs and tapping outside closes it.

## Planned features
